# 帧遇后台批量分析与暂停恢复设计规格

## 目标

让图片批量分析和视频精彩帧分析在用户按 Home、切换到其他应用或锁屏后继续执行，同时降低后台分析对前台应用流畅度、耗电和温度的影响。

用户主动暂停后可以退出帧遇；下次打开仍保持暂停，并由用户明确点击“继续”后从已提交的检查点恢复。应用进程被系统回收或意外中断时，未主动暂停的批次应由 WorkManager 或应用启动对账恢复。

## 已有基础

当前实现已经具备：

- WorkManager 唯一串行工作链。
- `SystemForegroundService` 和低优先级常驻通知。
- Room 批次、工作项、视频时间戳和执行代际检查点。
- 批次暂停、继续、取消、失败重试和启动对账。
- Worker 每秒最多更新一次前台通知。

本设计在这些边界上增量实现，不创建第二套任务队列，也不让 Activity 或 Compose 页面持有分析协程。

## 非目标

- 不承诺在用户从系统设置“强行停止”应用后继续运行。Android 会阻止该应用的后台任务，直到用户再次打开应用。
- 不通过保活、双进程、无障碍服务或定时唤醒规避 Android 和 HyperOS 的后台限制。
- 不并发运行多个模型任务来追求后台吞吐量。
- 不改变用户主动暂停的语义，也不在应用启动时自动恢复 `PAUSED` 批次。
- 不在本阶段增加新的第三方依赖。

## 方案比较

### 方案 A：后台保持全速

沿用现有 Worker，不感知应用前后台。实现最少、完成最快，但模型推理会持续占用 CPU，影响用户同时使用其他应用，也更容易触发温控。

### 方案 B：同一前台任务自适应降速（采用）

WorkManager 始终拥有任务；应用进入后台后，只在安全工作边界增加短暂让步，回到前台后取消人为延迟。任务 ID、执行代际和检查点不发生切换，因此没有前后台交接竞态。

该方案兼顾持续执行、可恢复性和设备可用性，是本次采用方案。

### 方案 C：后台仅在充电或设备空闲时运行

资源占用最低，但用户离开应用后任务可能长时间没有进展，不符合“可以慢，但希望继续处理”的目标。以后可以作为可选的夜间模式，当前不实现。

## 运行架构

```text
Compose 页面
    │ 开始 / 暂停 / 继续 / 取消
    ▼
BatchAnalysisScheduler / VideoAnalysisWorkScheduler
    │ 唯一串行 WorkRequest
    ▼
WorkManager CoroutineWorker
    │ 长任务期间 setForeground
    ▼
SystemForegroundService + 常驻通知
    │
    ├─ Room：批次、工作项、执行代际、视频时间戳
    ├─ AppVisibilityTracker：前台 / 后台
    └─ BackgroundPacingPolicy：正常速度 / 后台让步 / 温控等待
```

Activity 退出或 Compose 页面销毁不会取消 Worker。前台和后台只改变节流策略，不迁移任务、不新建 Worker，也不重置模型结果。

## 应用可见性与后台节流

### 可见性来源

`FrameYuApplication` 注册 `Application.ActivityLifecycleCallbacks`，由进程级 `AppVisibilityTracker` 统计已启动 Activity：

- 至少一个 Activity 处于 started 状态：`FOREGROUND`。
- 所有 Activity 都已 stopped：`BACKGROUND`。

状态只保存在内存中；进程新建且尚无 Activity 时按 `BACKGROUND` 处理。无需新增 `lifecycle-process` 依赖。

### 节流边界

`BackgroundPacingPolicy` 是纯 Kotlin 策略，输入应用可见性和温控状态，输出下一安全边界需要等待的时间：

- 前台且温度正常：不增加延迟。
- 后台且温度正常：每次重模型推理单元完成后等待 200 ms。
- 温控要求等待：沿用现有温控轮询，优先级高于后台节流。
- 批次已暂停或取消：不等待，立即进入持久化收尾。

图片批次只在 `CLASSIFICATION`、`EMBEDDING` 和 `CONDITIONAL_DETECTION` 工作项完成后节流，避免给纯数据库或轻量质量阶段增加无意义延迟。视频分析在每个已提交 checkpoint 的采样帧之后节流。延迟发生前必须先提交结果和断点；协程取消必须原样传播。

200 ms 是首版固定策略。真机验收根据 Redmi K70 Pro 的前台应用流畅度、温度和吞吐量决定是否调整，不在首版提供复杂档位设置。

## 前台通知

运行中的批次继续使用 `batch-analysis` 低优先级通知渠道和 `dataSync` 前台服务类型。通知展示：

- 当前阶段。
- 已处理数量和总数。
- 失败数量。
- 当前处于“正常速度”或“后台友好模式”。
- 有足够样本时显示粗略剩余时间，并明确使用“约”字样。

通知提供两个操作：

- “暂停”：发送到应用内、`exported=false` 的 `BatchAnalysisActionReceiver`。Receiver 使用 `goAsync()` 调用现有 scheduler 的持久化暂停接口；Runner 在下一个安全工作边界退出。
- “打开帧遇”：打开 `MainActivity` 并定位到对应批次状态页。

通知操作必须携带批次 ID 和不可变 `PendingIntent`。无效、缺失或不存在的批次 ID 只记录错误，不修改其他批次。

视频单任务通知本阶段保持现有行为；后台节流同时覆盖视频分析。统一视频通知操作可以在后续交互迭代中补充。

## 暂停、退出与恢复语义

### 用户只是离开应用

按 Home、切换应用、锁屏或从最近任务界面划走 Activity 时：

- 不修改批次状态。
- Worker 继续以前台任务运行。
- 进入后台友好节流。
- 返回应用后恢复正常速度。

HyperOS 仍可能根据用户设置限制进程。应用在批次页显示简短说明，引导用户在需要长时间分析时允许后台运行，但不强制跳转系统设置。

### 用户主动暂停后退出

点击页面或通知中的“暂停”时：

1. Room 批次状态写为 `PAUSED`，待运行工作项写为 `PAUSED`，执行代际失效旧执行。
2. 当前原子模型调用允许完成；结果与 checkpoint 提交后，Runner 读取到暂停状态并正常退出。
3. WorkManager 节点以受控成功结束，前台通知消失。
4. 退出或重开应用后仍显示 `PAUSED`，不得启动对账自动续跑。
5. 用户点击“继续”后，工作项恢复为可运行状态，提升执行代际并入队新的唯一 WorkRequest。

已完成工作项和视频已提交时间戳不会重算。

### 异常中断

- WorkManager 节点仍有效时，由 WorkManager 恢复或重试。
- 应用进程重新创建时，启动对账只处理 `QUEUED` 和 `RUNNING` 批次，并补入缺失执行。
- 被中断的 `RUNNING` 工作项恢复为可重试状态，从最近成功提交的阶段或视频时间戳继续。
- 用户从系统设置强行停止后，只有再次打开帧遇才允许对账恢复。
- `PAUSED`、`CANCELLED` 和终态批次不参与自动对账。

## 剩余时间估算

Worker 内使用本次活跃执行的处理增量和单调时钟计算滑动平均吞吐量：

- 处理样本少于 30 个或观测时间少于 30 秒时不显示 ETA。
- 暂停时间不计入活跃耗时。
- 前后台模式切换后重新建立采样窗口，避免使用前台速度估算后台耗时。
- 只在通知中显示分钟级或小时级粗略值，不写入 Room，不作为完成承诺。

进程重建后 ETA 暂时消失，积累足够样本后重新出现。

## 错误处理与安全

- 通知暂停失败时保留运行状态、继续显示运行通知并记录可诊断日志；不得假装已暂停。
- Receiver 完成异步操作后必须调用 `PendingResult.finish()`。
- 后台节流延迟不得吞掉 `CancellationException`。
- 可见性计数不得出现负数；Activity 重建和配置变化期间采用短暂后台状态是允许的，不影响任务正确性。
- Worker 和通知操作继续通过批次执行代际隔离旧请求，旧 Worker 不得覆盖新状态。
- 后台运行不读取新的媒体权限，也不上传任何媒体或分析结果。

## UI 文案

批次运行页增加：

> 可以切换到其他应用，分析会通过通知继续运行；后台时会自动降低速度。

暂停页增加：

> 已保存当前进度。退出帧遇后仍会保持暂停，下次打开可继续。

运行状态显示“正常速度”或“后台友好模式”。“暂停”表示协作式暂停，允许当前单项分析完成后停止，不承诺瞬时终止模型调用。

## 测试与验收

### JVM 测试

- 前后台可见性状态转换和 Activity 计数边界。
- `BackgroundPacingPolicy` 的前台、后台、温控、暂停和取消决策。
- 通知展示数据和 ETA 的样本阈值、模式切换重置。
- 通知操作的批次 ID 校验。
- 主动暂停不会被启动对账恢复，`QUEUED/RUNNING` 会被恢复。

### Android 仪器测试

- 通知包含“暂停”和“打开帧遇”操作。
- 通知暂停把 Room 批次置为 `PAUSED`，且 Worker 在安全边界退出。
- 暂停后重建 Activity 和进程仍保持暂停。
- 后台后 Worker 继续增加已完成计数，返回前台后仍是同一批次和检查点。
- 通知打开操作定位到对应批次。

### Redmi K70 Pro 真机验收

1. 启动至少 1,000 个工作项的批次，记录前台 2 分钟吞吐量。
2. 按 Home 并使用其他应用 5 分钟，确认通知存在、完成数持续增加且没有闪退。
3. 返回帧遇，确认同一批次继续且恢复正常速度。
4. 从通知暂停，等待前台服务退出；划走应用后重开，确认仍为暂停状态。
5. 点击继续，确认从原完成数增长，不创建重复批次。
6. 强制停止后重开，确认运行中批次通过启动对账恢复；主动暂停批次不恢复。
7. 记录后台温度、PSS、吞吐量和失败数，与全速基线比较。

验收不卸载应用、不清除数据，始终使用覆盖安装保留权限与批次状态。

## 实现范围

预计修改或新增以下边界：

- `AppVisibilityTracker`：进程可见性。
- `BackgroundPacingPolicy`：后台让步决策。
- `BatchAnalysisRunner` 和 `RoomVideoAnalysisWorkerRunner`：安全边界节流。
- `BatchAnalysisWorker`：通知状态、ETA 和操作。
- `BatchAnalysisActionReceiver`：通知暂停。
- `MainActivity`：通知打开批次路由。
- `BatchAnalysisScreen`：后台运行与暂停恢复说明。
- Manifest、对应 JVM/仪器测试和项目文档。

不新增数据库表或迁移，不新增依赖，不更改媒体删除和导出逻辑。
